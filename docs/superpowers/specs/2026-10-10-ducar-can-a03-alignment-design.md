# DUCAR CAN A0.3 对齐设计规格

日期：2026-10-10  
目标工程：`E:\DUCAR\DUCAR CODE\new platform\DUCAR_N32G45x_Project`  
协议基准：`DUCAR_CAN通信协议A0.3.xlsx`

## 1. 目标

让目标工程中可实现的 DUCAR CAN 报文与 A0.3 一致，并在 `app_param.h` 提供明确的 CAN 协议版本参数，使上位机读取 F200 时能判断固件使用的协议版本。对协议中定义了字段、但工程没有可靠数据源或业务接口的项目，不伪造数据、不擅自接入危险业务；保持现有 NAK/无效值行为，并记录缺口。

## 2. 已确认的协议差异与设计决策

### 2.1 参数与 F200 版本响应

A0.3 的 F200 响应包含：软件主版本、软件次版本、硬件版本和 CAN 协议版本。当前参数分别来自 `APP_PARAM_PACKAGE_V_VERSION`、`APP_PARAM_PACKAGE_T_VERSION`、`APP_PARAM_HW_VERSION`；当前配置为 V01、T9、V01。工程当前只输出三个版本字节，且协议版本在发送函数中硬编码。

设计：

- 在 `app_param.h` 增加 `APP_PARAM_CAN_PROTOCOL_VERSION`，A0.3 对应值为 `0x03`。
- F200 统一按 A0.3 布局输出 8 字节：`Data0=V主版本`、`Data1..2=T次版本数值（U16，小端）`、`Data3=硬件版本数值`、`Data4=协议版本`、`Data5..7=FF`。
- 当前参数示例的响应为 `01 09 00 01 03 FF FF FF`。
- T 次版本字段在工作簿中标注为 U8、长度却为 2 字节；按字段长度及版本数值用途，本方案暂按 U16 小端解释。若客户实际规定为其他编码，需在实现前纠正。
- 协议版本宏是固件构建参数，不另行占用 Flash 存储。

### 2.2 查询报文数据源

将已有查询处理按 A0.3 字段定义逐项复核，确保请求 PGN、DLC、响应 ID、字节位置、字节序、NA/保留值和真实数据源一致。已确认的参数映射保持如下：

- F205：厂家名称，来源 `APP_PARAM_MANUFACTURER_NAME`。
- F206：软件/电池型号名称，来源 `APP_PARAM_BAT_TYPE`（按用户已明确的映射）。
- F20B：额定电压和额定容量，分别来源 `APP_PARAM_BAT_VOLTAGE`、`APP_PARAM_BAT_CAPACITY`。
- F230：SN 写入继续按 TP RTS 声明的实际长度接收；F231/F232 按 A0.3 的查询和日志传输格式复核，不改变已确认的数据编码。
- 没有可靠数据源的 F203、F20C、F22E 等查询继续返回协议定义的拒绝/NAK，不填充臆测值。

### 2.3 周期发送和时基

A0.3 周期表要求：

| PGN | 周期 |
| --- | ---: |
| F218 | 50 ms |
| F20D、F20E、F219、F21A–F21F | 100 ms |
| F20F–F214 | 200 ms |
| F215–F217 | 500 ms |
| F220 | 1000 ms |
| F221 | 100 ms |

当前通信任务约每 1 ms 调用 CAN 任务，而 CAN 周期计数按 5 ms/tick 计算，造成发送快约 5 倍；部分 F220/F221 还被放在 500 ms 调度组。实现时统一使用毫秒时基，并按上表重排调度。同步检查 TP 超时、等待计数和 DETD 活跃窗口等依赖相同 tick 假设的计时逻辑，避免只修周期表后引入超时偏差。

当前周期发送还受 DETD 有效窗口控制。方案保留 DETD 作为唤醒/活跃条件，并让收到有效 F22F 心跳时刷新现有 5 秒活跃窗口；窗口外不改变当前休眠策略。若 A0.3 对窗口/心跳有更具体定义，以协议原文为准。

### 2.4 F218 字段映射与并联信息

A0.3 的 F218 Data0 含 DETD、DETC、BMR、ID、D-MOS、C-MOS、预充 MOS、KEY。当前工程有 `mcu_det_load`、`mcu_detd`、`mcu_detc`、`mcu_2nd_det` 等信号，但现有代码证据不能确认 `mcu_det_load` 或 `mcu_2nd_det` 哪个代表协议中的 BMR/ID。实现不得按名称猜测；此映射需核对原理图/信号定义后再写入。

并联状态没有可用的 peer 数据源时，Data1/Data2 的双位状态统一报协议规定的 NA；并联告警/保护字段在没有 peer 时按协议的无并联默认值处理，不合成实际状态。

### 2.5 告警、保护和无效值

- 对只有布尔型故障源的字段，仅在 A0.3 允许时输出 0/1；对现有业务源明确区分等级的字段，按协议输出 1/2/3 等级，不压成布尔值。
- 当前 AFE/保护数据源缺少的位不从相邻状态推导。若协议允许且硬件功能不存在，使用规定的 0/NA；若功能存在但软件无数据源，列为实现缺口，不声称完全覆盖。
- F221 峰值电流尚无可靠采集源时，Data0 按协议无效值 `FF FF` 输出，不输出看似有效的 0。
- F220 当前无效字段继续按 A0.3 定义发送 `FF FF`；有真实源的字段再映射，不改变其他字段定义。

### 2.6 控制报文

现有实现的 E800、PF09、E000、E100、E300、E200、E600、E700、E900 和 PF/F2 RTC 等业务入口保留，并逐项核对 A0.3 的 ID、DLC、数据字段、响应 PGN/状态和副作用。

A00/B00/C00 当前没有可确认的业务 API；其中模拟/调试数据不得注入真实保护或 MOS 控制链路。没有定义安全行为和实现接口前，继续按未支持命令回复 NAK，不新增模拟功能。

## 3. 范围外

- 不改 CAN 物理层波特率、引脚、终端电阻或线束；工程配置的 500 kbit/s 只能说明软件配置，不能替代实车/台架验证。
- 不重构 UDS、Bootloader、AFE 采样、Flash 布局、SOC 或保护策略；只检查 CAN 改动对共享数据读取的影响。
- 不把“所有协议行都有响应”作为目标；没有数据源或安全业务接口的命令保留明确拒绝行为。

## 4. 实施与验证策略（待规格批准后执行）

1. 更新/新增 A0.3 契约测试：F200 版本布局、F205/F206/F20B 参数源、查询/控制报文 ID 与 DLC、F218 字段位、周期发送时序、F221 无效值和 TP 时限。
2. 修正 CAN 毫秒时基及调度分组；测试周期至少覆盖 50/100/200/500/1000 ms，检查允许误差与计数回绕。
3. 用静态/契约测试确保未支持查询与控制仍拒绝，且不存在将模拟值写入安全状态的路径。
4. 运行工程现有 CAN 契约测试，并执行 Keil 工程全量编译；不能以单元测试通过替代 Keil 编译结果。
5. 台架验证：500 kbit/s 实际链路、主机过滤 ID、请求/响应 ID、周期报文间隔、DETD/F22F 活跃窗口、TP 长度及超时。

## 5. 执行时收敛的定义缺口

用户已要求执行并继续，按上述方案实施；以下决策同时记录于执行进度文件：

1. F218 的 BMR/ID 没有可靠数据源时报告未接入0，不使用负载检测和二级熔断检测冒充；实际硬件源仍是后续待接入项。
2. F200 T 字段使用 U16 小端，依据2字节字段长度及全协议小端规则；工作簿的 U8 类型标注仍需同步纠正。
3. 有效 F22F 请求刷新5秒活跃窗口，使主机可以在DETD未接入时维持普通CAN周期通信。
4. E200/E300/E600/E900接受完整有效字段或带预留字节的8字节帧；E700保持协议明确规定的4字节。
5. TP.DT尾帧固定DLC8，有效字节后补FF，真实数据长度以RTS长度为准。
