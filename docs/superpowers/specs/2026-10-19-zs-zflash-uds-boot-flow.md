# 宗申 ZCANPRO `.zflash` UDS 升级兼容设计

## 目标

让现有 APP 和 BOOT 的 UDS 实现按提供的 `ZS_ECU_Flash_20250401.zflash` 流程工作，同时保留工程现有的 DUCAR UART/CAN 升级流程。

## 依据

- `.zflash` 地址配置：物理请求 `0x7A0`，物理响应 `0x7A8`，功能寻址 `0x7DF`。
- 提供的《Q_ZSJS 239-2020 BootLoader 设计规范》规定了编程会话 `10 02` 时从 APP 切换到 BOOT、UDS 服务、指纹格式、CRC16 校验和程序依赖检查。
- `.zflash` 文件规定了具体服务顺序和数据值。
- 协议文件中的内容用于确定设备与刷写工具之间的报文行为；代码修改范围仍以你的需求和下面的设计为准。

## 设计

### APP 预编程阶段

- APP 负责进入扩展会话、一级安全访问、供应商/硬件/软件版本 DID，以及编程前的功能寻址命令。
- 扩展会话下接受并执行 `10 83`、`85 82` 和 `28 83 03`；按请求抑制肯定响应。
- `28 83 03` 仅在扩展会话且一级解锁后允许开启。开启普通通信抑制后，持续时间不少于 5 分钟；期限从第一次抑制开始计算，不因持续收到 UDS 请求而续期。到期后恢复普通通信。期限使用 RTC 完整日历秒数计时，设备在 STOP 休眠期间也计入；休眠中的 RTC 周期唤醒检查到期后恢复 APP 外设与普通通信。为覆盖整秒分辨率，运行期限按 301 秒设置。RTC 时间回拨时重新设置差分基准，不把校时回拨误算成跨午夜，避免提前恢复。
- 普通应用 CAN 报文被静默后，仍允许 APP 接收 `0x7A0` 上的物理 UDS 请求。
- 收到物理寻址的 `10 02` 后，APP 仅在扩展会话且一级解锁后准备 BOOT“等待升级包”状态；不接受带抑制肯定响应位的 `10 82`，确保 `50 02` 确实发送完再复位。重复进入当前扩展会话 (`10 83`) 保留已取得的一级解锁，使 `.zflash` 顺序可用。

### BOOT 编程阶段

- BOOT 发现 UDS“等待升级包”状态后，以编程会话启动 UDS 服务端；从 `0x7A0` 接收物理请求，并从 `0x7A8` 发送响应。
- “等待升级包”状态是掉电保持的恢复入口。APP 已交接到 BOOT 后，如果下载或校验阶段中断、设备复位，BOOT 继续停留并等待下一次升级；重新刷写既可以按原 APP 交接流程直接从编程阶段开始，也可以从 `.zflash` 预编程阶段重新开始。后一种路径在 BOOT 内接受扩展会话、安全访问、版本 DID 和功能寻址静默命令，再由物理 `10 02` 在 BOOT 内切换到编程会话，不复位、不跳回 APP。新一轮预编程会话会清除上一次未完成的易失传输状态；只有新一轮完整下载、CRC 和依赖检查成功后才允许启动 APP1。
- BOOT 预编程阶段的 DID `F18A/F193/F189` 与 APP 返回值一致；供应商名、软件 V/T 版本取自 APP 的 `app_param.h`。`28 83 03` 和 `85 82` 按 APP 相同的扩展会话/一级安全条件校验，并按功能寻址和抑制位静默响应；BOOT 不运行 APP 普通通信或 DTC 记录，因此这两项在 BOOT 内只确认命令，不操作 APP 外设/状态。
- BOOT 内物理 `10 02` 仅在扩展会话且一级解锁后受理，拒绝抑制肯定响应；发送 `50 02` 后在 BOOT 内切换到编程会话，保留 `WAIT_PACKAGE`，不复位。APP 交接后直接进入编程会话的原路径仍然有效。
- 正常启动且 APP 有效时仍立即跳转 APP，不增加 BOOT 监听窗口；仅原有“等待升级包”状态提供上述恢复入口。
- 编程阶段服务框架覆盖 `.zflash` 的 DID `F180`、指纹 `2E F184`、下载/传输/退出 `34/36/37`、CRC `31 01 02 02`、可选擦除 `31 01 FF 00`、依赖检查 `31 01 FF 01` 和复位 `11 03`。二级安全访问 `27 09/0A` 的消息处理已接入，但因 KeyConst 未确认，Key 请求当前返回 NRC `0x22`；因此整条 `.zflash` 刷写尚不能完成。
- `.zflash` 的第一个下载项必须完整收到 9 字节 ASCII 标记 `BMS-DUCAR`，并校验其内容和数据 CRC；标记缺失或内容不匹配时，升级流程报错并拒绝继续。
- 提供的 `.zflash` APP 下载项设为 `erase_ecu_memory_mode=0`，流程 XML 没有单独的 `31 FF00` 项。BOOT 因此在 APP `34` 下载获准后按页惰性擦除 APP1（每页在首次写入前擦除）；若客户端显式发送 `31 FF00`，仍按经校验的镜像范围预擦除。此规则针对 BOOT 内接收 UDS 升级；APP 正常运行时的自升级继续使用 APP2 暂存。
- 不执行这个识别标记或任何下载到 RAM 的驱动代码。内部 Flash 擦除和写入使用 BOOT 现有的页擦除/写入接口。这是你选择的实现方式，会偏离规范中“将 FlashDriver 下载到 RAM 并执行”的要求。
- BOOT 内的 UDS 应用镜像直接擦写 APP1。写入与擦除地址限制在 APP1 代码范围；下载中断时 `WAIT_PACKAGE` 保持不变，复位后 BOOT 继续等待并允许从头重刷。所有检查通过后写入带镜像长度和 CRC32 的 `APP1_READY` 状态；收到 `11 03` 并发送完响应后复位，BOOT 再核验 APP1 向量表与整包 CRC32，确认有效后转为 `APP_VALID` 并启动 APP1。现有 APP2 搬运流程保留给 DUCAR UART/CAN 等其他升级入口。
- 将 `F184` 的 8 字节指纹写入现有 APP 数据库专用记录区。前 4 字节按 BCD 日期校验，后 4 字节按 ASCII 设备编号校验，并允许 `.zflash` 实际使用的 `00` 字节。

### 返回 APP

- BOOT 验证 APP1 并复位后，APP 从默认会话启动，普通 CAN 输出恢复。
- 默认会话下接受 `.zflash` 的恢复命令 `28 80 03`、`85 81` 和 `10 01`；恢复阶段不能继续抑制普通通信。

### 安全与地址边界

- 实现与 `SeednKey_20250401.dll` 一致的安全访问算法和常量，不能默认当前全零常量与 DLL 一致。规范给出了 KeyConst 算法，但没有常量值；DLL 静态检查只确认导出 `GenerateKeyEx`，尚未取出 KeyConst，因此 APP/BOOT 当前必须拒绝解锁（NRC `0x22`），不可标记为安全访问兼容。
- 擦除或写入前先检查地址和长度计算；RAM 地址对应的 FlashDriver 数据仅接收并参与 CRC 校验，绝不调用执行。
- 除 BOOT 内 UDS 升级直接写 APP1 及使用现有 BOOT 数据库状态标志外，不改变 APP 自升级、现有 DUCAR BOOT 升级协议与 Flash 分区。

## 当前缺少的文件

`.zflash` 引用了 `FlsDrv.s19` 和应用文件 `rt5_crc32_release.s19`，但这两个 S-record 文件目前不在 `.zflash` 同目录或代码仓库中。因此代码可以按安全范围处理下载地址，但尚不能用实际文件核对 S-record 地址段、长度和分块情况。

## 验收条件

1. APP 能在 `0x7A0` 接收 `.zflash` 的预编程流程，并按要求抑制功能寻址肯定响应。
2. APP 在交接 BOOT 前发送 `50 02`；BOOT 随后能直接处理下一条物理请求，不要求重复切换会话。
2a. 若升级在下载/校验阶段中断或掉电导致设备留在 `WAIT_PACKAGE`，BOOT 重启后仍等待升级；同一 `.zflash` 可以从预编程开头重新执行，包含 BOOT 内的扩展会话/预编程命令和 `10 02` 会话切换，不需要 APP 可运行，也不增加正常启动等待时间。完整校验后进入 `APP1_READY`，BOOT 再核验 APP1 并启动。
3. BOOT 从 `0x7A8` 回复，校验每组 `34/36/37` 传输和 CCITT-FALSE CRC；不依赖 `.zflash` 中未列出的 `31 FF00` 步骤，按页擦写 APP1 合法范围，并拒绝越界请求。
4. 第一个下载项的数据完整等于 9 字节 `BMS-DUCAR` 标记并通过 CRC；不匹配时停止升级，不执行任何下载代码。
5. `FF01` 检查及 `11 03` 成功后，BOOT 记录 `APP1_READY`；复位后核验 APP1 的向量表和 CRC32，无效或不完整的数据不能启动。
6. APP1 验证通过并启动后，APP 能接受恢复通信/DTC 的命令并恢复普通输出。
7. `28 83 03` 抑制普通通信至少 5 分钟，RTC 计时包含 STOP 休眠；到期后由运行任务或下一个20秒 RTC 唤醒点恢复，`28 80 03` 可提前恢复。
8. 现有 DUCAR UART/CAN 升级流程保持可用。

## 尚待确认的实现输入

安全访问所需常量必须从提供的 DLL 中静态确认，或通过已知 Seed/Key 测试向量确认。当前只确认 DLL 是 32 位 PE 并导出 `GenerateKeyEx`，本机无可用反汇编器，未执行 DLL；常量无法据此确认。代码将 APP/BOOT 的 Key 校验设为 fail-closed，并返回 NRC `0x22`；`27 01/02` 与 `27 09/0A` 仍未实现兼容，收到经确认的四字节 KeyConst 或已知向量后再启用。

当前 `.zflash` 将第一个下载项命名为 `FlsDrv.s19`，实际 S19 文件尚未提供，无法确认它经工具解析后的下载数据是否恰为 9 字节 `BMS-DUCAR`。实现按用户要求将它作为必需标记块；若实际下载数据不是这 9 字节，设备会按设计拒绝升级，需要先同步修正下载文件或 `.zflash` 下载项。
